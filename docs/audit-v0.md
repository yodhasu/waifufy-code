# v0 audit (verified findings)

Generated from the audit workflow. Every finding was checked by an adversarial verifier. Refuted findings are left out. When a verifier corrected the fix, the corrected fix is used.

## robustness

### Facts

I found the timers and listeners in the client are fine: chat.ts registers every listener and its one setInterval (the clock, line 305) once inside createChat, and start() adds none, so returning to the menu repeatedly leaks nothing. Each choice menu rebuilds its input element, so the keydown listeners from otherInput go away with it. link.ts keeps handlers in a Set that lives outside the socket, so reconnecting does not duplicate them. Path traversal in assets.ts is blocked correctly on Windows; the real problem in that file is the decodeURIComponent crash. Shutdown works: lib.rs drops the child's stdin, the sidecar's 'end'/'close' handlers call session.close() (q.close() kills the CLI subprocess) and then process.exit, and lib.rs kills the child after 3s. If the app crashes, the OS closes the pipe, so the sidecar still exits. CREATE_NO_WINDOW is applied only in release builds, as intended.

SDK facts for whoever fixes this:
- Query.close() ends the subprocess and stops further messages, but the iterator ends with a 'Claude Code process aborted by user' error (Ry() in sdk.mjs), and pump() emits that as {t:'error'}. Suppress it after an intentional close.
- In streaming-input mode, q.supportedCommands(), supportedModels(), accountInfo() and initializationResult() can be called right after query(); they wait for the initialize handshake. There is no need to wait for system/init, which may only arrive after the first user message.
- Auth failures arrive as an assistant message with `error: 'authentication_failed' | 'billing_error' | 'rate_limit' | ...` (sdk.d.ts:3776).
- Other system subtypes to handle: 'api_retry' (attempt, max_retries, retry_delay_ms, error) and 'local_command_output' (content).
- query() also accepts `stderr: (data) => void` for CLI logs and `pathToClaudeCodeExecutable`. The SDK ships a platform CLI package (claude-agent-sdk-win32-x64 is installed).
- Node on this machine is v24.15.0; type stripping is on by default in Node >=22.18 and >=23.6.
- waifufy.config.json sets idleFps/reactionFps to 60.
- Live2D assets resolve to C:\Users\mybook\Documents\Work\waifufy\assets (models/, voices/ present).

### Confirmed findings

- **[critical] A malformed %-escape in an asset URL crashes the whole sidecar (unhandled rejection)** (link/src/assets.ts:30 + link/src/server.ts:16)
  - Evidence: serveAsset is async and calls decodeURIComponent(pathname.slice(...)) outside its try block. server.ts calls it as `void serveAsset(pathname, res)`, so nothing catches the rejection. A GET like /assets/%E0%A4%A throws a URIError, which becomes an unhandled rejection, and Node 24 exits the process on that by default. The request also never gets a response. The HTTP server needs no token and replies with CORS *, so any local process (or a web page that guesses the random port) can kill the link. A model or voice filename containing a stray '%' would do the same. Nothing respawns the sidecar after this (see the next finding).
  - Fix: Wrap the decode in try/catch and reply 400. Put the whole body of serveAsset in try/catch, or use `.catch(() => reply(res,500,...))` in server.ts. Add process.on('unhandledRejection'|'uncaughtException') logging in server.ts so one bad request cannot end the session.

- **[critical] Sidecar failure is invisible: if node is missing, too old, crashes, or the port is taken, the app hangs on a blank menu forever** (app/src-tauri/src/lib.rs:94-96, app/src/link.ts:20-38, app/src/main.ts:33)
  - Evidence: If spawn fails, lib.rs only calls eprintln!, and a release build has windows_subsystem="windows" (main.rs:2), so nobody sees it. If node exists but can't run .ts (Node <22.18/23.6 has no default type stripping), or the process dies later (EADDRINUSE on http.listen has no 'error' handler, or the crash above), lib.rs never notices: there is no try_wait watcher and no restart. On the page, connect() awaits a promise that only resolves on the first onopen, and it retries every 400ms forever with no timeout and no UI. main.ts:33 `await connect()` blocks everything after it, so the menu never gets 'Summoning Rem…', sessions never load and Rem never loads. After a mid-session crash, link.ts reconnects in silence, outbox grows without bound, and chat keeps saying 'Rem is working'.
  - Fix: The fix is the same in substance, with these details: (1) In lib.rs, keep the spawn error (and the result of a `node --version` check for 22.18 or newer) in Link state, and expose it through a `link_status` command. (2) Redirect the child's stdout and stderr to a log file in app_log_dir. Start a watcher thread that polls try_wait and emits a 'link-down' event with the exit code and the last lines of the log. Optionally restart the child, with a cap on retries. (3) In server.ts, add http.on('error') and a process.on('uncaughtException') handler that logs and exits non-zero. (4) In link.ts, race the first connect against a timeout and against link_status/link-down, and reject on failure. Back off between retries and report status (connecting, down, error) to the UI. Cap or drop the outbox while disconnected, and on reconnect, end the 'working' state in chat. (5) In main.ts, wrap the connect() call in try/catch. On failure, show a full-screen error in the visual novel's style (for example "Rem can't wake up: Node 22.18+ is required") with Retry and Open log buttons, instead of a blank menu. A banner like "Reconnecting to Rem…" covers drops mid-session.

- **[major] When a session dies (not logged in, CLI crash, spawn error), the UI keeps accepting input that goes nowhere** (link/src/session.ts:252-260, link/src/server.ts:44-48, app/src/chat.ts:570-573)
  - Evidence: pump() emits {t:'error'} and then {t:'ended'}, but server.ts keeps `session` pointing at the dead Session. A later 'say' calls inbox.push() on an iterator nobody reads, so it is silently dropped. On the client, 'ended' only sets running=false and calls updateRibbon(). The dialogue still says 'Rem is getting ready' (set in start(), chat.ts:674), and every later send() calls narrate('Rem is working') (chat.ts:507), which never resolves. Nothing offers 'restart' or 'back to menu'.
  - Fix: In server.ts, set `session = undefined` when that session's pump ends (pass an onEnded callback and compare identity). In chat.ts 'ended': narrate a clear line ('Rem lost her connection to Claude Code: <reason>') with choices 'Resume this session', 'Back to title', and disable #msg until one is picked. If send() runs while no live session exists, show a toast instead of narrating 'working'.

- **[major] Not logged in / auth errors only show a cryptic toast; the explanatory text is dropped and /login cannot be run** (link/src/session.ts:304-313, 273-279)
  - Evidence: The CLI reports auth problems as a synthetic assistant message: `error: 'authentication_failed'` (SDKAssistantMessageError, sdk.d.ts:3776) plus a text block such as 'Not logged in · Please run /login'. With includePartialMessages, the synthetic message has no stream_event, and the 'assistant' case only reads tool_use blocks. So the user sees the toast 'Claude: authentication_failed' and nothing in the dialogue. terminal_slash_commands (which includes /login) are filtered out of the picker, and nothing calls q.accountInfo() at start, so a first-time user has no way forward. system subtypes 'api_retry' (sdk.d.ts ~3663) and 'local_command_output' (sdk.d.ts:5519) are ignored too: retries look like a hang, and local command output is never shown.
  - Fix: In the 'assistant' case, when m.error is set (or the message has no matching stream events), forward its text blocks as dialogue text. Map error codes to friendly lines ('Rem can't reach Claude: please run `claude` in a terminal and /login'). Call q.accountInfo() after init and emit an 'account' message so the title screen can show who is logged in and warn early. Handle api_retry as a narration ('Claude is busy, retrying 2/10 in 4s…') and local_command_output as Rem text.

- **[major] Two quick 'start' messages orphan a running Claude Code process** (link/src/server.ts:40-46)
  - Evidence: handle() is async: `session?.close()` runs first, then `await loadSettings()` and `await loadHistory(...)`, and only then `session = new Session(...)`. Two 'start' messages in flight (double Enter or double-click on a session, or a reconnect replaying the outbox) both close the same old session, both build a new Session, and the second assignment overwrites the first without closing it. That leaves a live CLI subprocess and query that keeps broadcasting text, tools and permission prompts into the active chat. The 'say' and 'interrupt' paths use the same unguarded global.
  - Fix: Close the old session and assign the new one together, synchronously, after the awaits. Use a generation counter so a 'start' that has been superseded drops out:  ```ts let startGen = 0 case 'start': {   const gen = ++startGen   const settings = await loadSettings()   const history = m.resume ? await loadHistory(m.resume, m.cwd) : []   if (gen !== startGen) return            // a newer start won; don't spawn a CLI   session?.close()                        // close + assign with no await between   session = new Session(m.cwd, m.resume, settings.userName, broadcast)   return broadcast({ t: 'started', ... }) } ```  Also bump startGen in the 'end' case (`++startGen; session?.close(); session = undefined`), so a 'start' still in flight cannot bring a session back after 'end'. On the client (chat.ts:677), ignore repeat begin clicks until 'started' arrives. The client could also dedupe 'start' messages in the outbox.

- **[major] Server messages carry no session identity, so the old session's late events leak into the new chat** (link/src/server.ts:27-30,41-45; link/src/session.ts:185-188,257-259; app/src/chat.ts:511-513)
  - Evidence: Every Session broadcasts through the same `broadcast`. close() calls q.close(), and pump's iterator then ends or throws asynchronously, so the old session emits {t:'error', message:'Claude Code process aborted by user'} (Ry() in sdk.mjs) and {t:'ended'} after the new session's 'started' when switching with 'start'. A refreshStats() still in flight also emits old stats. chat.ts only filters on `active`, which start() sets to true right away, so a stale error toast/backlog line, running=false and old gauges land in the new session. close() also never resolves the old `pending` permission promises and never emits ask_cancel for them.
  - Fix: 1. Give each Session a generation number (`sid`, an incrementing counter in server.ts) and stamp it on every message the Session emits. Do it in one wrapper, e.g. `const emit = (m) => broadcast({...m, sid})`, which also covers the TagParser callbacks built in the constructor. Also send `sid` in 'started'. 2. On the client, save `sid` from 'started' and drop any message whose sid differs. Because 'started' itself can come after a stale 'ended', also ignore every message that has a sid until the matching 'started' has arrived. For example, have the client choose the id and send it with 'start', or have start() clear the current sid so stale messages are dropped until the new 'started' sets it. 3. In Session.close(), set `this.closed = true` and have emit return early when it is set. That silences the late 'error', 'ended', 'stats' (from refreshStats) and 'ask_cancel' messages. Explicit handling of pending entries is optional, because the SDK already aborts each canUseTool signal on cleanup and session.ts:229-233 resolves them. Clearing `pending` in close() is harmless and keeps it tidy. 4. Optional: in pump's catch, skip the 'error' emit when `this.closed` is set. The `closed` guard in emit already covers this.

Also add a client message 'resync' (or reuse 'sessions') that triggers the same snapshot, so a reconnect inside chat.ts can rebuild the chat too.

### Facts

The SDK is 0.3.309 with a bundled native CLI 2.1.309 (link/node_modules/@anthropic-ai/claude-agent-sdk-win32-x64/claude.exe). Facts checked against sdk.d.ts and sdk-tools.d.ts, plus string searches of the binary:

Its options also include title, displayName, description, decisionReason, blockedPath, defaultToNo, suppressAlwaysAllowRule, toolUseID, agentID, requestId and matchedAskRule; session.ts uses only suggestions and signal.

- ExitPlanMode: the schema has only a deprecated allowedPrompts field plus an index signature. Use updatedPermissions setMode to choose acceptEdits.
- TodoWrite is off by default (needs CLAUDE_CODE_ENABLE_TASKS=false). The live tools are TaskCreate/TaskUpdate/TaskList/TaskGet, with outputs TaskCreateOutput{task:{id,subject}}, TaskUpdateOutput{success,taskId,statusChange} and TaskListOutput{tasks[]}. Read structured results from SDKUserMessage.tool_use_result.
- Agents run in the background by default. The tool_result has status 'async_launched', and completion arrives as system task_notification (with tool_use_id). By default only tool_use/tool_result blocks from subagents are forwarded (with parent_tool_use_id); `forwardSubagentText: true` forwards their text too. Matching tool_result to tool by tool_use_id is correct, and the stream_event filter on parent_tool_use_id is correct.
- SDKStatusMessage (system/status) carries permissionMode for mode changes; it is not handled now.
- ui.ts renderMarkdown escapes HTML, so plan and detail rendering is not open to XSS.
